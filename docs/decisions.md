# Architecture Decision Records

## ADR-0001: Translatable fields stored as JSONB, not `*_translations` tables

**Decision:** Every translatable field (title, slug, description, etc.) is a single JSONB column shaped `{ "de": "...", "en": "...", "tr": "..." }`, validated with helpers in `shared/schemas/i18n.ts`. Language codes are not a hardcoded TypeScript union; they come from the `languages` table.

**Why:**
- Acceptance criteria require adding a 4th language from the admin panel *without a deploy* — JSONB needs no DDL change, only a new key in existing JSON objects.
- A single row per entity keeps public-facing queries (page render, sitemap, listings) simple — no N-table joins per language.
- Admin forms (language tabs + completeness indicator + "copy from another language") are simpler to implement against one JSON object than N related rows.

**Trade-off accepted:** Postgres can't enforce slug uniqueness per language with a DB constraint on a JSONB column. Slug uniqueness is enforced in the service layer inside a transaction before insert/update.

## ADR-0002: `page_blocks.data` as a Zod discriminated union

**Decision:** Each block type has its own Zod object schema; all of them combine into `blockSchema = z.discriminatedUnion('type', [...])` in `shared/schemas/blocks/index.ts`. The Drizzle column is untyped `jsonb`; validation happens at the application boundary (admin API write, and a `safeParse` guard before rendering).

**Why:** One source of type truth shared between admin editor forms, the write-side API validation, and the public renderer's `BLOCK_REGISTRY`. A `safeParse` failure at render time (e.g. stale data from a removed block type) skips that block instead of crashing the page.

## ADR-0003: `site_settings` as a key-value JSONB table

**Decision:** `site_settings(key varchar primary key, value jsonb)` instead of a wide fixed-column table. Known keys are validated against `siteSettingsSchemas` in `shared/schemas/site-settings.ts`.

**Why:** New settings (added throughout later phases: SMTP, cookie categories, analytics IDs, etc.) never require a migration.

## ADR-0004: Slug uniqueness enforced in the service layer

**Decision:** Because slugs live inside JSONB (`pages.slug`, `services.slug`, etc.), per-language uniqueness is checked in `server/services/**` inside a DB transaction rather than via a SQL `UNIQUE` constraint.

**Why:** Consequence of ADR-0001. Mitigation: all slug writes go through service functions — there is no direct Drizzle insert/update of these tables outside the service layer.

## ADR-0005: TypeScript pinned to `^6`, not the newer `7.x` line

**Decision:** `typescript` is pinned to `^6` in `devDependencies`.

**Why:** `typescript-eslint` (used by `@nuxt/eslint`) does not yet support the `7.x` compiler line at the time this project was scaffolded (`typescript-eslint does not support TS 7.0`). Revisit this pin once `typescript-eslint` adds support.

## ADR-0006: Content-module public URLs use a fixed English section segment, not a translatable one

**Decision:** Services, branches and blog posts are public at `/services`, `/services/:slug`, `/branches`, `/branches/:slug`, `/blog`, `/blog/:slug` (locale-prefixed per `prefix_except_default`, e.g. `/en/services/...`). The section segment (`services`/`branches`/`blog`) is a fixed English path in code; only the **item's own slug** is per-locale and admin-editable (already the case for services/blog_posts; `locations` gained a `slug` jsonb column in this phase to match).

**Why:** prompt.md's reference URLs (`/leistungen/...`, `/en/services/...`, `/tr/hizmetler/...`) imply the *section* segment itself is translatable per sector/language, which would require it to be admin-configurable data rather than a file-based Nuxt route — the page-builder's catch-all (`app/pages/[[...slug]].vue`, ADR from Phase 4) already proves that pattern works for CMS pages, but content-module list/detail views need their own dedicated Vue templates (grids, detail layouts), not block rendering. Fully generalizing this was out of scope for Phase 5. Revisit if/when a sector template needs a non-English section slug — the fix is additive (a small "section slugs" settings table + reading it in these route files), not a rearchitecture.

## ADR-0007: Damage-wizard recommendation is a summed-score threshold match, not a decision tree

**Decision:** Each answer option carries an admin-editable `score` (0-100). `evaluateAnswers()` sums the score of every selected option across all questions, then picks the rule with the highest `minScore` that the total still meets or exceeds (rules sorted descending by `minScore`, first match wins), defaulting to `repair` if no rule matches (i.e. a `minScore: 0` rule should generally exist as the floor).

**Why:** A branching decision tree (each question's answer determines which question comes next) would require a graph structure in the admin UI and could produce dead ends if an admin edits questions without updating branches. A flat sum-and-threshold model lets an admin add/reorder/remove questions and options independently — every combination of answers always produces *some* total score, and rules are just thresholds against it, so the config can never end up in an unreachable or contradictory state.

## ADR-0008: Honeypot field must stay schema-permissive; detection happens only in the route handler

**Decision:** The `companyWebsite` honeypot field on `contactMessageSchema` and `appointmentSubmissionSchema` is `z.string().optional()` with no length or emptiness constraint. `server/api/contact.post.ts` and `server/api/appointments.post.ts` check it *after* a successful `safeParse` and, if filled in, return `{ success: true }` without writing a row or sending email.

**Why:** An earlier version used `.max(0, 'Spam detected')` on the field, which made a filled honeypot fail Zod validation and return a `400` with `fieldErrors.companyWebsite` in the response — directly revealing to any bot which field is the trap (and that the trap exists at all). Keeping the schema permissive means a bot that fills every field always gets an identical `200 {"success":true}` response whether or not it tripped the honeypot, same as a real submission.

## ADR-0009: `/llms.txt` and `/llms-full.txt` select the language via `?locale=`, not a per-locale path

**Decision:** `server/routes/llms.txt.get.ts` and `llms-full.txt.get.ts` are single Nitro routes that read `?locale=` (defaulting to the site's default language) rather than living at `/en/llms.txt`, `/tr/llms.txt`, etc.

**Why:** A true per-locale path would need its own file-based route per language, which conflicts with languages being pure runtime data (ADR-0001) — the whole point is that adding a 4th language never touches a file. A query param keeps one route serving every language. Documented as a deliberate simplification of prompt.md §15.4's "her dil için ayrı versiyon" requirement, in the same spirit as ADR-0006.

## ADR-0010: PATCH routes must strip Zod-defaulted keys the caller never actually sent

**Decision:** Every admin PATCH route validates with `inputSchema.partial().safeParse(body)` and then passes the result through `keysActuallySent(parsed.data, body)` (`server/utils/partial-update.ts`) before handing it to the service layer, instead of passing `parsed.data` directly.

**Why:** Discovered as a live data-loss bug during Phase 7 testing: several input schemas have fields with `.default(...)` (e.g. `services.isFeatured`, `services.content`). Zod's `.partial()` only makes a field *accept* `undefined` — it does **not** stop that field's own `.default(...)` from firing when the key is simply absent from the request body. A real partial PATCH (e.g. `{ slug: {...} }` only) came back from `safeParse` as `{ slug: {...}, content: {}, isFeatured: false }`, and the service layer's `db.update(...).set({ ...input })` then overwrote `content`/`isFeatured` with those defaults, silently destroying existing data. The admin UI's own forms happened to always submit every field (so this never manifested through the UI), but the API itself did not honor true partial-update semantics — `keysActuallySent` fixes that at the boundary for every module in one place rather than requiring every input schema to avoid `.default()`, which would remove a genuinely useful feature (defaults on *create*).

## ADR-0011: Applying a sector template backs up content into one `site_settings` snapshot, not a full backup system

**Decision:** `applySectorTemplate()` (`server/services/sector-template.service.ts`) writes every content-bearing table (pages, page_blocks, services, locations, faqs, faq_categories, testimonials, damage_wizard_*, menus, menu_items, blog_posts, blog_categories) into a single JSON blob under `site_settings.lastTemplateBackup` before truncating those tables and running the new template's seed function. There is exactly one backup slot — applying a second template overwrites the first snapshot.

**Why:** prompt.md §6 requires the "Apply template" flow to "back up existing content" before switching, but a real point-in-time backup system (versioned, restorable, off-database storage) belongs with the rest of Phase 10's backup/restore work (`docs/deployment.md`), not bolted onto a template switch. A single JSON snapshot is a genuine safety net against "I clicked the wrong template" — an admin (or a future restore endpoint) can still read `site_settings.lastTemplateBackup` — without pretending this is a backup strategy a production deployment should rely on. Restricting the whole endpoint to the `owner` role reflects how destructive it is: every piece of public content on the site is replaced in one call.

## ADR-0012: CSP allows `'unsafe-inline'` for `script-src` and `style-src`

**Decision:** The Content-Security-Policy set in `nuxt.config.ts`'s `routeRules['/**'].headers` includes `'unsafe-inline'` in both `script-src` and `style-src`, alongside `'self'` and the specific third-party origins actually used (`googletagmanager.com` for analytics, `openstreetmap.org` for the lazy-loaded map iframe's `frame-src`).

**Why:** Nuxt embeds the SSR hydration payload as an inline `<script>` on every single page, and `UiAnalyticsLoader` injects a short inline `gtag(...)` init script — a CSP without `'unsafe-inline'` (or a nonce/hash-based policy) would break hydration on every page load. `style-src` needs it too: Vue's `:style` bindings and the SSR theme injection (`app/composables/useTheme.ts`'s `<style>:root{...}</style>`) are both inline. A properly strict nonce-based CSP is achievable in Nitro but needs either the `nuxt-security` module or hand-rolled per-request nonce plumbing through the render pipeline — out of scope for this pass. What this CSP still buys: no arbitrary third-party script/style origins, no arbitrary frames, no plugins (`object-src 'none'`), and no base-tag hijacking (`base-uri 'self'`) — it blocks the most common injection vector (loading an attacker-controlled *external* script) while accepting that inline-script mitigation would need more investment. Revisit if `nuxt-security` (or equivalent) is added later.

## ADR-0013: HTTP response compression is deferred to the Phase 10 reverse proxy, not built into Nitro

**Decision:** `nuxt.config.ts`'s `nitro.compressPublicAssets` pre-compresses built static assets (`_nuxt/*` JS/CSS) with gzip and brotli at build time. Dynamic SSR HTML responses are served uncompressed by the Nitro `node-server` directly — no compression middleware is added to the app itself.

**Decision context (measured, not assumed):** a mobile Lighthouse run against the production Docker build (bare container, port 3000, no reverse proxy) scored Performance 80, Accessibility 100, Best Practices 100, SEO 100 — short of the ≥90 performance target in prompt.md §13, and the two biggest deductions (First Contentful Paint, Largest Contentful Paint) both stem from uncompressed HTML/document transfer over Lighthouse's simulated throttled mobile network.

**Why defer instead of fixing here:** prompt.md's own deployment architecture (§10) puts Caddy in front of the app as a reverse proxy with automatic HTTPS — Caddy compresses responses (gzip/zstd) by default with zero configuration. Adding a second compression layer inside the Node process (e.g. an h3/Nitro compression middleware) would be redundant work once Caddy is in place, and tuning compression behavior in two places instead of one is a real place to introduce bugs. **This is a known, measured gap, not a claim that the ≥90 target is already met** — re-run Lighthouse against the Caddy-fronted deployment once Phase 10 ships `docs/deployment.md`, and only add in-app compression if that measurement still falls short.

## ADR-0014: Public UI strings merge DB overrides into vue-i18n at runtime, on top of static locale-file fallbacks

**Decision:** The `translations` table (schema existed since Phase 1 but was never wired up) now has a service layer, admin CRUD (`/admin/translations`), and a public cached endpoint (`GET /api/translations`, `{ "contactForm.send": { de: "...", en: "...", tr: "..." }, ... }`). `app/composables/useDbTranslations.ts`, called from `app.vue` alongside the existing `useTheme()`, fetches that map and calls `$i18n.mergeLocaleMessage(locale, ...)` for each locale — overriding the static `i18n/locales/*.json` values wherever a DB row exists for that key, and falling back to the JSON file's value otherwise. `server/db/seed/core-translations.ts` seeds the DB with every key's current JSON-file value on a fresh database (`server/db/seed/run.ts`, unconditionally, like `seedBaseLanguages()` — not sector content, so it's independent of `--template=`).

**Why:** prompt.md §14 is explicit that the locale files are "only fallback/default values" and "the real values are kept in the DB and edited from the admin panel's 'Translations' screen" — Phases 6-9 had instead been treating the static JSON files as the actual source of truth for every new UI string (`cookieConsent.*`, `languageBanner.*`, `map.*`, `contactForm.*`), which worked but didn't match the spec's explicit architecture. This ADR corrects that: the JSON files are now genuinely just compiled-in defaults, and every one of those strings is live-editable without a deploy.

**Why the merge happens in `app.vue` rather than a dedicated plugin:** `useTheme()` already established the exact same pattern (an unawaited `useFetch` in `app.vue`'s setup, relied upon to resolve before Nuxt finalizes the SSR response) for injecting the theme's `<style>` tag — same mechanism, same file, same reasoning, so `useDbTranslations()` reuses it instead of introducing a second way of doing SSR-blocking data fetches.

**Known limitation:** `PUT /api/admin/translations/:key` replaces the entire `values` object for that key (normal PUT/replace semantics) — it does not merge per-language. The admin UI's own edit form always round-trips the complete set of languages (fetches the row, pre-fills every language's current value, submits all of them back), so this is only a footgun for a *direct* API call that sends just one language's value; do the same fetch-then-full-replace dance in any new caller.

## ADR-0015: The admin panel's own UI is localized by a standalone i18n system, not `@nuxtjs/i18n`

**Decision:** Every admin page/component uses `app/composables/useAdminI18n.ts` — a small custom composable backed by plain JSON catalogs (`app/i18n/admin/{de,en,tr}.json`) with dot-path key lookup, `{param}` interpolation, and a `currentLocale → 'de' → raw key` fallback chain — instead of the public site's `useI18n()`/`@nuxtjs/i18n`. Each admin user's language preference is their own `users.locale` column value (the column existed since Phase 2 but was unused until now), switchable in-panel via `AdminLanguageSwitcher` (`app/components/admin/LanguageSwitcher.vue`), which `PATCH`es `/api/admin/users/:id` with `{ locale }`.

**Why not reuse `@nuxtjs/i18n`:** that module is wired to public URL routing (`prefix_except_default`, hreflang, `switchLocalePath`) — the admin panel is a single fixed-path SPA-like section (`/admin/**`) that must never gain locale-prefixed URLs, and per-admin-user language choice is unrelated to (and must not interfere with) a visitor's public-site locale. A second, independent i18n mechanism keeps these two concerns from leaking into each other. Reusing the DB-backed `translations` table (ADR-0014) was also rejected: that table stores public-site content strings editable by non-technical staff, whereas admin-chrome labels are developer-owned UI copy — plain JSON catalogs compiled into the bundle are the right fit, matching how the public site's own static locale files work as a *fallback* layer.

**Server-side permission change required:** `server/services/users.service.ts::updateUser()` previously called `requireRole(actingRole, 'admin')` unconditionally, which blocked an `editor`-role user from ever calling `PATCH /api/admin/users/:id` — even on their own record to change their own `locale`. The role gate is now skipped when the target user is the acting user (self-service update), while self-role-change and self-`isActive`-change remain explicitly forbidden regardless of role, and the `admin` role gate still applies in full when acting on *another* user's record.

**Known limitation:** the login page (`/admin/login`) has no authenticated user yet, so `useAdminLocale` always renders the `'de'` default there regardless of the eventual account's saved preference — this is unavoidable without exposing locale via an unauthenticated mechanism (e.g. a cookie set before login), which was judged not worth the complexity for one screen. E2E specs (`e2e/admin-auth.spec.ts`, `e2e/security.spec.ts`, `e2e/translations.spec.ts`) target the German login-page strings (`'E-Mail'`, `'Passwort'`, `'Anmelden'`) for this reason, while post-login assertions rely on the test admin's `locale: 'en'` (set in `e2e/global-setup.ts`) for stable English text elsewhere.

**Vue gotcha hit while writing catalog strings:** an HTML entity (`&ge;`, `&rarr;`) embedded in a JSON translation value does not render as its glyph through `{{ t(...) }}` interpolation — Vue inserts interpolated text as a raw text node without entity-decoding it. Use the actual Unicode character (`≥`, `→`) directly in the JSON string instead.

## ADR-0016: The admin panel is a bespoke Tailwind build, not Metronic/KTUI

**Decision:** `app/components/admin/**` (Sidebar, Topbar, Breadcrumb, DataTable, Modal, ConfirmDialog, FormField, ToastContainer, MediaPicker, RichTextEditor, SeoPanel, and every block editor) is hand-written Vue 3 + Tailwind CSS v4, with no dependency on `@keenthemes/ktui`, the `metronic-tailwind-html-integration` repo, or any KTUI vanilla-JS runtime. `/admin/**` also runs fully SSR (no `routeRules: { '/admin/**': { ssr: false } }`), the same rendering mode as the public site.

**Why this deviates from prompt.md §16:** §16 asked for KTUI's component runtime (cloned and adapted from the MIT-licensed Metronic Tailwind integration repo), admin-only `ssr: false`, and a documented `THIRD_PARTY_LICENSES.md`. None of that was implemented — the admin UI kit was built from scratch against Tailwind directly, starting in Phase 2, and this decision was never written down at the time, which is itself the gap this ADR closes retroactively (§11 requires every non-trivial technical decision to land in this file *when it's made*, and this one didn't).

**Consequence, assessed now rather than defended:** the visual outcome (collapsible sidebar, topbar, breadcrumb, card-based content, clean tables — prompt.md's actual stated goal for this section) is met; the specific *implementation mechanism* prompt.md asked for is not. Losses from skipping KTUI: no ready-made drawer/dropdown/tabs primitives (each was hand-rolled instead, more code but zero third-party licensing surface to track), and no `THIRD_PARTY_LICENSES.md` was ever needed since nothing MIT-licensed was vendored in. Keeping SSR on for `/admin/**` (rather than `ssr: false`) turned out to be load-bearing for this project's actual architecture: `useAdminI18n()` (ADR-0015) and several admin pages rely on `useFetch`/`useAsyncData` resolving during SSR the same way public pages do (see CLAUDE.md's Phase 2 "Known dev-environment gotcha" about `useRequestFetch()` on full page loads) — switching to `ssr: false` now would require reworking that data-loading pattern across every admin page for no clear benefit, since admin SEO was never a real requirement here anyway.

## ADR-0017: GEO/AI-search follow-up pass — IndexNow, 404 log, per-bot robots rules, short-answer/structured facts, new blocks

**Decision:** A post-Phase-10 pass closed several remaining §15 (SEO/GEO) gaps in one batch:
- `server/plugins/not-found-logger.ts` logs every public 404 (path + hit count) into a new `not_found_logs` table; `/admin/redirects`'s new "404 log" tab lets an editor turn a logged path into a redirect with one click (`POST /api/admin/not-found-logs/:id/create-redirect`), then clears the log entry.
- `site_settings.robots.botRules` adds a real per-bot allow/disallow toggle (`shared/constants/ai-bots.ts` lists the well-known AI crawlers from prompt.md §15.4) rendered into `robots.txt`, on top of the freeform `extraRules` textarea that already existed.
- `pages.seo`, `services.seo`, `blog_posts.seo` all gained `shortAnswer` (a 2-3 sentence direct-answer summary rendered at the top of the page/service/post) and `focusKeyword` (admin-only, drives a checklist, never rendered). `services` also gained structured facts (`priceFromCents`, `durationMinutes`, `warranty`, `insuranceInfo`) shown in a facts table on the service page and folded into its `Service` JSON-LD as an `Offer`. `blog_posts` gained an author byline (`authorName`, `authorRole`, `authorPhotoMediaId`) shown on the post and in its `BlogPosting` JSON-LD `author`.
- `app/components/admin/SeoPanel.vue` is a new reusable component (meta title/description with character *and* approximate pixel-width bars via canvas `measureText`, a live Google-style search-result preview, focus keyword, short answer, noindex, and a small self-scoring checklist) — wired into the Pages, Services, and Blog Posts admin forms so all three share one SEO-editing implementation instead of three near-duplicates.
- Two new page-builder block types: `comparison-table` (columns + rows, each cell translatable) and `certificates` (E-E-A-T trust badges: title/issuer/image per item).
- `server/middleware/markdown-export.ts` serves a clean Markdown version of any page/service/blog-post via `Accept: text/markdown` content negotiation (never a separate route, so it can never shadow the normal HTML page at the same URL) — togglable via `site_settings.seoDefaults.markdownExportEnabled`.
- `server/services/indexnow.service.ts` pings the shared IndexNow API (Bing/Yandex) on every page publish/service save/blog-post save, best-effort and silently no-op if disabled or unreachable (same non-blocking principle as the SMTP no-op from Phase 6) — controlled by `site_settings.indexNow.{enabled,key}`, with the key auto-generated on first enable and served back at `/{key}.txt` for IndexNow's domain-verification step.

**Why the city×service "similarity warning" and the full site-wide SEO report / bulk SEO editor screens from §15.3/§15.5 are *not* part of this pass:** city×service landing pages already work today with zero new code — `pages` already supports an arbitrary admin-created slug and full block content, which is exactly what a `/standorte/berlin-mitte`-style page needs. Only the *duplicate-content similarity warning* is a genuine gap, and a site-wide SEO report/bulk editor are both meaningfully sized screens of their own; both are left for a follow-up pass rather than rushed here.

**Visual-fidelity gap found and closed (a genuine, previously-unaddressed miss):** a manual browser comparison against the actual reference sites named in prompt.md §1 (`carglass.de` — blocks bot traffic, 403; `junited-autoglas.de` — reachable) exposed that the public site had never received a visual-design pass: no icon library was wired into any public block despite `@lucide/vue` already being a project dependency (used only in the admin panel), several schema fields for icons (`services.iconOrMediaId`, `whyUsFeatureSchema.icon`, `howItWorksStepSchema.icon`) were defined but never rendered anywhere, three blocks (`ServiceCards`, `BlogPreview`, `BranchFinder`) had hardcoded English fallback text (`"No services published yet."` etc.) that had escaped the i18n system entirely, and none of those three list blocks linked their cards to the actual detail page. Fixed: `app/utils/feature-icons.ts` is a small curated icon-name registry (shield/clock/wrench/star/etc., using `@lucide/vue` — no new dependency) selectable from the admin block editor and rendered on the public `WhyUs` block; `ServiceCards` now fetches and renders `iconOrMediaId` (falling back to a generic wrench icon) and links each card to its service page; `BranchFinder` links to branch pages with MapPin/Phone icons; `BlogPreview` links to post pages; the three hardcoded strings moved into `i18n/locales/*.json`. `heroBlockSchema` gained an optional `badges: translatableOptionalText()[]` field (junited-autoglas.de-style short trust signals under the CTA, e.g. "Free loaner car") with a matching admin editor and public render, and `Hero.vue` gained a subtle dot-pattern decorative background for when no editor-chosen image is set, so the section never reads as a single flat color block. None of this required new brand assets (logo, real photography, a real color palette) — those still need to come from the actual company once available, same open item prompt.md itself flags — but the *code's own rendering pipeline* no longer silently drops the icon/link/trust-signal content types the schemas were already designed to carry.

**FAQ block redesigned after cross-session design consultation with the `ev-mobil` project (same user, sibling app on the same server):** the flat, single-list `faq-accordion` block was replaced with a search + category-tabs + numbered-accordion "help center" layout, directly inspired by (and, per the user's explicit request, matching the interaction pattern of) `ev-mobil`'s own `/sss` page. Rather than guessing at the design rationale from its CSS alone, this session messaged the other Claude session actually working on `ev-mobil` and got confirmation of several non-obvious behavior details before implementing: (1) the design was that session's own choice, not a specific user brief — free to adapt; (2) its color tokens are that project's own theme variables, not a cross-project brand preference — this project's own `primary` theme color is used instead of copying hex values; (3) on mobile (<1024px in the original), the sidebar tabs stay a vertical list, never becoming a horizontal scrolling pill row — implemented here by simply never applying the two-column grid below `lg:`, so the tabs render as normal stacked full-width buttons; (4) selecting a category resets the search box and any open accordion item; (5) search mode fully replaces the tabs+panel layout with a flat, category-badge-labeled result list, rather than living alongside it. One implementation improvement over the original: accordion open/close uses a CSS Grid `grid-template-rows: 0fr → 1fr` transition (the sibling session's own suggestion, given as a caught limitation in its original `max-height: 600px` approach) instead of a fixed max-height, so an answer of any length animates correctly with no clipping risk.

Real gap this surfaced and fixed in the same pass: the `faq_categories` table (and the category-grouping UI this block now depends on) existed since Phase 1 but had zero rows in the actual seeded content — every seeded FAQ had a `NULL` `category_id`. The new block handles that gracefully (an "General"/`Allgemein` pseudo-category collects uncategorized FAQs, and the tabbed sidebar disappears entirely — falling back to a single flat panel — when there's only one category total, so it never renders a single, pointless tab), but the `autoglass` seed template was also updated to actually create and use two real categories ("Repair & Costs", "Appointments & Service"), since a template that ships a real, working feature only in its unused/degenerate state isn't really finished. `generic-service` was deliberately left with zero categories — consistent with it being the intentionally lighter skeleton template.

**§16 (admin panel theme) follow-up, same session:** re-reading prompt.md §16 against the running admin panel (and, for direct comparison, the actual live Metronic Demo1 at keenthemes.com — reachable, unlike carglass.de) showed the same underlying issue as the public site: functionally complete (collapsible sidebar with icons, topbar, breadcrumb, card-based content, clean tables — the actual visual outcome ADR-0016 already claimed as met) but visually flat next to Metronic's reference — no shadows on cards/tables, no hover feedback on table rows, dashboard stat cards were plain text with no icon accent. Closed with generic Tailwind polish (not copied Metronic markup/CSS, consistent with ADR-0016's licensing stance): `shadow-sm` added to `AdminDataTable.vue` and the 10 admin list pages sharing its `rounded-xl border` card wrapper pattern, `hover:bg-slate-50` row feedback added to the 8 of those pages using the shared draggable-row markup, sort-direction unicode arrows (▲▼) replaced with actual `ChevronUp`/`ChevronDown` icons, and the dashboard's three stat cards gained a colored rounded icon badge (blue/amber/emerald, reusing `@lucide/vue` icons already a project dependency) plus a hover lift/shadow transition, matching the icon-badge pattern real dashboards in this space commonly use without reproducing Metronic's specific implementation.

**Incidental cleanup found during the same visual QA pass:** repeated `pnpm test:e2e` runs across this session had accumulated 35 fake appointments (`contact_name LIKE 'Rate Test%'`) and 10 fake contact messages (`email LIKE 'rate-%'` / `'playwright-%'`) in the dev database — leftovers from `e2e/security.spec.ts`'s rate-limiter test and `e2e/contact-form.spec.ts`, which both write real rows against whatever database `pnpm dev` is pointed at (there's no separate E2E database in this project's setup). Deleted directly; not a code bug, just something to remember to clear periodically when running the E2E suite repeatedly against a database you also want to keep looking realistic in the admin UI.

**A real display bug caught during that same visual pass:** the public service detail page and its admin edit form both checked `priceFromCents !== undefined` to decide whether to show a price — but the column has no DB default, so an unset price reads back as `null`, not `undefined`, and `null !== undefined` is `true`. Every service without an explicit price silently showed "0,00 €" instead of hiding the price row. Fixed by switching both checks to `!= null` (loose equality, deliberately catching both `null` and `undefined`), which also required widening the TypeScript field types from `number | undefined` to `number | null` to match what the API actually returns for an unset integer column.

**Framework bug hit (and worked around, not just patched) while building the IndexNow key-verification file:** a Nitro/Nuxt file-based route whose filename mixes a bracket param with a literal suffix in the *same path segment* — `server/routes/[key].txt.get.ts`, intended to match `/:key.txt` — is not split by the underlying router (rou3) into a `key` param plus a static `.txt` suffix the way the generated `nitro-routes.d.ts` type (`'/:key.txt'`) implies: at runtime the entire bracket token becomes one parameter literally named `"key.txt"` (confirmed by logging `event.context.params` directly, since `getRouterParam(event, 'key')` silently returns `undefined`), and its *captured value* still carries the `.txt` suffix. Stripping the suffix by hand made the route *work*, but it did not explain a second, far more serious symptom found immediately after: **that same route file broke the entire public site — `GET /` (and every other page) started 404ing**, reproduced twice from a clean `pnpm dev` restart, and confirmed by mechanically deleting the one file: the homepage came back the instant `server/routes/[key].txt.get.ts` was removed. The most likely explanation is that Nitro's scanner, unable to correctly parse the mixed bracket+suffix filename into a proper single-segment dynamic route, registers something closer to a wildcard that outranks Nuxt's own catch-all page-render fallback in rou3's matching order — but the exact internal mechanism wasn't traced further once a safe fix was in hand. **Fix:** serve the key file from a `server/middleware/indexnow-key.ts` middleware instead (matching the existing `redirects.ts`/`markdown-export.ts` pattern) — it inspects `event.path` by hand with a regex and only ever `return`s a body for the one exact matching request, so it can't register a competing route pattern at all. **Takeaway for any future route:** never name a file-based server route `[param].<literal>.<method>.ts` (a bracket segment plus a literal suffix in one path segment) — even setting aside the param-name/value quirk above, it has been observed to break routing for unrelated paths sitewide. Use a middleware for that shape of match instead.

**Not revisited:** given the admin UI already exists, is fully functional, tested (`e2e/admin-auth.spec.ts` and others run against it), and localized (ADR-0015), retrofitting it onto KTUI at this point would be a rewrite with no user-facing benefit — the risk of introducing regressions outweighs conforming to a spec detail about *how* the same visual result should have been achieved. If a future requirement genuinely needs a KTUI-specific behavior (e.g. a component KTUI has that would take significant effort to hand-roll), evaluate adopting it for that one component rather than a wholesale migration.
