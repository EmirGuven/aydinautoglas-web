# CLAUDE.md

## Project summary
A dynamic, multi-sector-adaptable corporate website + admin panel. First deployment: an auto glass company operating in Germany. Every piece of visible content (text, images, menus, pages, colors, logo, contact info, SEO fields) is managed from `/admin` — no hardcoded visible content in code. Same codebase can be re-pointed to other sectors by applying a different sector template (theme + menus + pages + blocks + seed content).

Stack: Nuxt 4 (SSR) + Vue 3 + TypeScript (strict), Nitro server routes (no separate backend), Tailwind CSS v4, PostgreSQL 17 + Drizzle ORM, Zod, `jose` (JWT), `argon2`, `sharp`, `@nuxtjs/i18n` + DB-backed translations, TipTap, pnpm, Vitest + Playwright.

Full spec: `prompt.md` (source of truth for scope). Implementation plan and phases: see the plan referenced in the conversation that created this project; this file is kept up to date as phases complete.

## Commands
- `pnpm dev` — start dev server (requires Postgres reachable via `DATABASE_URL`; see `docker-compose.dev.yml`)
- `pnpm build` / `pnpm preview` — production build / preview
- `pnpm lint` — ESLint
- `pnpm typecheck` — `nuxt typecheck` (vue-tsc)
- `pnpm test` — Vitest unit tests
- `pnpm test:e2e` — Playwright
- `pnpm db:generate` — generate Drizzle migrations from `server/db/schema/*`
- `pnpm db:migrate` — apply migrations (also runs automatically on container start)
- `pnpm db:seed --template=autoglass|generic-service` — seed a sector template
- `pnpm admin:create` — create the first admin user (CLI prompts, or `--email=`, `--name=`, `--password=`, `--role=`)

## Architecture rules
- API routes (`server/api/**`) stay thin; business logic lives in `server/services/**`.
- Every admin endpoint (`server/api/admin/**`) validates input with Zod (`shared/schemas/**`) and is protected by `server/middleware/admin-auth.ts`. Role checks happen in the service layer, not in routes.
- Public GET endpoints are cached (`defineCachedEventHandler` / route rules) and invalidated when the underlying content changes.
- **Translatable content is stored as JSONB `{ de, en, tr, ... }`** on the row itself (see ADR-0001 in `docs/decisions.md`), not in separate `*_translations` tables. Validate with the helpers in `shared/schemas/i18n.ts` (`translatableText`, `translatableRichText`, `translatableSlug`).
- **Page builder blocks** are a Zod discriminated union in `shared/schemas/blocks/index.ts`. See `docs/how-to/add-a-block-type.md` before adding a new block type.
- **Theme** is read from the single-row `theme` table and injected as a synchronous `<style>:root{...}</style>` via `useHead` in `app/app.vue` (`app/composables/useTheme.ts`) so there is no FOUC.
- **Settings** (`site_settings`) is a key-value JSONB table — add a new setting by adding a key + Zod schema in `shared/schemas/site-settings.ts`, never by migrating a new column.

## Code style
- All code, variables, and commit messages: English. User-facing text lives in i18n files (fallback only) or the database (source of truth).
- TypeScript strict everywhere.
- No hardcoded user-visible content in code — if it's visible on the site or in the admin UI, it belongs in the database or a translation key.
- Comments only where the *why* isn't obvious from the code.

## Don'ts
- Do not use the Google Fonts CDN (DSGVO) — self-host fonts.
- Do not copy Metronic's code — only take visual inspiration (layout language) for the admin UI.
- Do not add a `*_translations` table for new content types — follow the JSONB pattern (ADR-0001).
- Do not create git commits — this project is not using git yet (explicit user decision as of the initial planning session).
- Do not hardcode a fixed set of language codes anywhere — languages are data (`languages` table); adding a 4th language must require zero code changes.

**Layout gotcha:** `app/layouts/admin.vue`'s root `div` sets a base text color (`text-text dark:text-slate-100`) that most inner elements rely on via inheritance — an element that sets only light-mode text/border classes with no `dark:` counterpart will inherit correctly, but one that sets a *fixed light-only color* (e.g. hardcoded `text-slate-700` with no `dark:text-*`) will go invisible in dark mode. Always pair light text-color utilities with a `dark:` counterpart.

Phase 4 (page builder, all 16 blocks, public layout, dynamic page render) — done. Block schemas live one-per-file in `shared/schemas/blocks/*.ts`, combined into `blockSchema` (discriminated union) in `shared/schemas/blocks/index.ts`; `BLOCK_TYPES` and `defaultBlockData()` live there too — **any new block's default data must satisfy its own schema** (a required `translatableText()` field needs at least one non-empty-keyed language, e.g. `{ de: '' }`, not `{}`; a `.optional()` field should be omitted from the default entirely, not set to `{}`) — this exact mistake shipped once and was caught by `shared/schemas/blocks/index.test.ts`'s "every registered block type has valid default data" test; re-run that test after touching `defaultBlockData()`.

Public rendering: `app/pages/[[...slug]].vue` is the single dynamic catch-all (optional catch-all matches `/` too) that fetches `GET /api/pages?locale&slug` and renders `BlocksRenderer`. Blocks that pull from other tables (service-cards, testimonials, partners, branch-finder, faq-accordion, blog-preview) read through `server/services/content-read.service.ts` + public `server/api/content/*.get.ts` endpoints — those tables are empty until Phase 5 adds admin CRUD for them, so those blocks render an empty state until then; that's expected, not a bug. Rich text (`rich-text`, `image-text` blocks) is authored with the TipTap wrapper `app/components/admin/RichTextEditor.vue` and is sanitized server-side in `server/services/pages.service.ts` (`sanitizeRichTextFields`) before every save — never trust `v-html` on unsanitized content.

**Import rule:** always import from `shared/` using the `#shared` alias (e.g. `#shared/schemas/blocks`), never a relative `../../shared/...` path, in files under `app/`. A relative import from `app/pages/admin/pages/[id].vue` built and ran fine in dev but broke the **production** build only (`pnpm build` / Docker build) with a Rollup `UNRESOLVED_IMPORT` error — dev's on-demand transform tolerates path patterns that the production bundler's chunk-relative resolution doesn't. `#shared` (Nuxt 4's built-in alias for the root `shared/` directory) sidesteps this entirely and is shorter besides. Newer `server/` files also use `#shared` for the same reason, even though the original Phase 1-4 relative server imports never hit this bug.

Phase 5 (content modules: services, branches/locations, blog, FAQs, testimonials, partners) — done. Each module follows the same shape: `shared/schemas/<module>.ts` (Zod input schema) → `server/services/<module>.service.ts` (CRUD + slug-uniqueness check for slugged modules, following `docs/how-to/add-an-admin-module.md`) → `server/api/admin/<module>/**` (protected CRUD + `reorder.put.ts` for sortable ones: services, faqs, testimonials, partners) → `app/pages/admin/<module>/index.vue` (draggable flat list for sortable modules, `AdminDataTable` for locations, tabbed posts+categories for blog). Rich-text fields (`services.content`, `blog_posts.content`) are sanitized server-side via `server/utils/sanitize-rich-text.ts` — the same rule as page-builder blocks (Phase 4): never trust `v-html` on unsanitized content, and add sanitization to any *new* rich-text-bearing field's create/update path, not just the ones that already have it.

Public content pages (`app/pages/services/`, `app/pages/branches/`, `app/pages/blog/`) use a **fixed English section segment** in the URL (not a translatable one) — see ADR-0006 in `docs/decisions.md` for why, and what to do if a sector template later needs a localized section slug. `locations` gained a `slug` jsonb column in this phase (it had none before) to support a branch detail page — if you add a public detail page for any other table, check whether it already has a per-locale `slug` column first.

Phase 6 (damage wizard, appointment booking, contact form, email notifications, spam/rate protection) — done. `server/services/damage-wizard.service.ts` manages questions/options/rules (admin CRUD under `/admin/damage-wizard`) and `evaluateAnswers()` sums each selected option's `score` and picks the highest-`minScore` rule the total still meets (default `repair` if none match) — see ADR-0007 in `docs/decisions.md`. The public wizard (`app/components/blocks/DamageWizard.vue`) posts to `/api/damage-wizard/evaluate` and links to `/appointment`, a 5-step form (`app/pages/appointment.vue`: vehicle → service/branch → schedule → insurance → contact+consent) posting to `POST /api/appointments`. `server/services/appointments.service.ts` also exposes `toCsv()`, served at `GET /api/admin/appointments/export`.

**Honeypot spam protection** (`companyWebsite` field on both `contact` and `appointments` submission schemas) must stay a plain `z.string().optional()` — see ADR-0008. Never add a `.max()`/length constraint to a honeypot field: a schema-level rejection 400s and tips bots off that the field is being checked. Detection must happen only in the route handler (`server/api/contact.post.ts`, `server/api/appointments.post.ts`), which silently returns `{ success: true }` without writing a row when the field is filled in.

Rate limiting (`server/utils/rate-limit.ts::checkRateLimit`) is a simple in-memory fixed-window limiter applied to login (10/60s), contact (5/60s) and appointments (5/60s) — fine for a single-instance deployment; if this app is ever horizontally scaled, replace it with a shared store (Redis) since the in-memory map is per-process.

Email (`server/services/email.service.ts`) reads SMTP config from `site_settings.smtp` and no-ops with a console warning (never throws) when `smtp.host` isn't set, so form submissions always succeed even in environments without email configured. Templates are admin-editable under Settings → Email templates (`site_settings.emailTemplates`), with `{{name}}`/`{{email}}`/`{{message}}` placeholder substitution and built-in per-locale fallback text (`DEFAULT_TEMPLATES`) when a template field is left blank.

**Vue template gotcha:** literal `{{...}}` used as documentation text in a template (e.g. `Use {{name}} as a placeholder`) must be wrapped in `v-pre` (e.g. `<code v-pre>{{name}}</code>`) — writing `{{ '{{name}}' }}` is a parser error, not valid escaping.

**Docker verification gotcha:** if `curl http://localhost:3000/...` behaves unexpectedly right after switching between `docker-compose.dev.yml` (host `pnpm dev`) and the full `docker-compose.yml` stack, check `lsof -nP -iTCP:3000 -sTCP:LISTEN` first — a leftover host `pnpm dev` process binds `[::1]:3000` and macOS resolves `localhost` to `::1` before Docker's `0.0.0.0:3000` mapping, so curl silently hits the stale host process instead of the container. Kill the stale process (or stop `pnpm dev`) before trusting a curl-based health check when both are meant to be running.

Phase 7 (i18n routing finalization, SEO, cookie consent) — done. `app/composables/useLocaleSeo.ts` sets `<html lang>`, `rel=canonical` and `rel=alternate hreflang` links on every public page — call it with no args on a fixed-path page (list pages, `/appointment`; every active locale's path is derived via `useSwitchLocalePath`) or with an explicit `{locale: path}` map on a page with its own per-locale slug (CMS pages, services, branches, blog posts) so a locale missing a translation is simply skipped rather than emitting a broken hreflang. `app/composables/useContentLocalePaths.ts` shares that same map with `UiLanguageSwitcher` (in the header) so switching language on a detail page goes to the *actual translated content*, not the same slug re-interpreted in another locale — falls back to `switchLocalePath` when a page hasn't set it. `UiLanguageSuggestionBanner` offers (never forces) a switch to the visitor's browser language on first visit, remembered via `localStorage` — `detectBrowserLanguage` is disabled in `nuxt.config.ts` for this reason, per prompt.md §14's explicit "no forced redirect" rule.

**Known i18n limitation:** adding a language via Admin → Settings → Languages makes its content instantly editable everywhere (ADR-0001 still holds — ​that part is genuinely zero-code-change), but its **URL prefix** only starts routing after `nuxt.config.ts`'s `i18n.locales` array includes that code and the app restarts — `@nuxtjs/i18n`'s `prefix_except_default` strategy resolves locale prefixes at build/route-registration time, which a fully dynamic-from-DB scheme would require rearchitecting the whole app's routing to avoid. `docs/how-to/add-a-language.md` is corrected to say this plainly rather than the earlier (inaccurate) "zero deploy" claim.

SEO: `GET /sitemap.xml` (`server/services/sitemap.service.ts`) and `GET /robots.txt` are Nitro server routes, not static files — the old static `public/robots.txt` was deleted since a static file in `public/` shadows a same-path server route. Sitemap entries are built from `pages`/`services`/`locations`/`blog_posts` directly (published/non-noindex only) with per-URL `<xhtml:link hreflang>` alternates; `robots.txt` always disallows `/admin` and `/api` and appends the freeform text from Settings → Robots & bots (`site_settings.robots.extraRules`) — a lighter stand-in for full per-bot toggle UI (GPTBot, ClaudeBot, etc. — prompt.md §15.4), which is deferred; admins can still block/allow any bot by pasting raw `User-agent`/`Disallow` lines. `GET /llms.txt` and `/llms-full.txt` (`?locale=` query param — see ADR-0009) give AI crawlers a plain-text summary/full export.

JSON-LD (`app/composables/useJsonLd.ts`) is wired in: Organization+WebSite site-wide (`server/api/json-ld/organization.get.ts`, cached, in `app/layouts/default.vue`), `Service` + `BreadcrumbList` on a service page, `AutoRepair`(LocalBusiness) + `BreadcrumbList` on a branch page, `BlogPosting` + `BreadcrumbList` on a blog post, `FAQPage` on the `FaqAccordion` block. **Gotcha:** unhead dedupes head tags by `key` *globally*, not per call-site — give every `useJsonLd()` call-site its own `useId()`-derived key prefix (already done), or a second call elsewhere with the same numeric index silently overwrites the first one's script tag.

**Redirects** (`/admin/redirects`, `server/services/redirects.service.ts`) is a full admin module (the `redirects` table existed since Phase 1 but had no service/UI until now) plus `server/middleware/redirects.ts`, which 301/302s a matching `GET` before Nuxt's router sees it (only matters for full document loads — external links, bookmarks, crawlers — not `<NuxtLink>` client transitions, which is exactly where a redirect is needed). A slug change on a page, service, location, or blog post **automatically** records a 301 from the old locale-prefixed URL to the new one (`recordSlugChangeRedirects`, called from each module's `update*` service function) — see ADR-0007-adjacent reasoning in ADR-0010 below for why the update functions had to start fetching the *previous* row first.

**Found and fixed a live data-loss bug** while testing the above: every admin PATCH route validates with `schema.partial().safeParse(body)`, but a schema field with `.default(...)` (e.g. `services.isFeatured`, `.content`) still gets defaulted back in in `parsed.data` even when the caller never sent that key — `.optional()` doesn't stop a sibling `.default()` from firing on a missing key. `server/utils/partial-update.ts::keysActuallySent(parsed.data, rawBody)` strips any key the raw request body didn't actually contain before the result reaches the service layer; every one of the 14 admin PATCH routes now wraps its `parsed.data` this way. See ADR-0010. The admin UI's own forms always sent every field, so this never surfaced through the UI, but a direct API call using a true partial payload would have silently wiped unrelated fields — apply `keysActuallySent` to any *new* PATCH route too.

DSGVO cookie consent (`app/composables/useCookieConsent.ts`, cookie-based, categories from `site_settings.cookieBanner.categories`) gates `UiAnalyticsLoader` (Google Analytics only loads after "analytics" consent) and `UiLazyMap` (an OpenStreetMap embed on the branch detail page — static preview + "Load map" button, auto-loads only if "functional" consent was already given). `UiCookieConsentBanner` offers Accept all / Necessary only / Customize.

Don't spend time chasing this further; only worth revisiting if a *non-standard-port* production deployment is ever needed.

Phase 9 (performance, accessibility, E2E tests, security review) — done.

**Security headers**: `nuxt.config.ts`'s `routeRules['/**'].headers` sets X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, Strict-Transport-Security, and a Content-Security-Policy. The CSP allows `'unsafe-inline'` for `script-src`/`style-src` — see ADR-0012 for why (Nuxt's inline hydration payload and the SSR theme `<style>` tag both need it; a nonce-based strict CSP would need the `nuxt-security` module) — and explicitly allow-lists `googletagmanager.com` (analytics) and `openstreetmap.org` (the lazy-loaded branch map iframe). Adding any *new* third-party script/frame/fetch origin means adding it here too, or it silently breaks under CSP.

**Fonts**: already DSGVO-compliant with zero code changes needed — the theme's `fontFamily` default (`system-ui, sans-serif`) is a system font stack, not a web font, so there's nothing to self-host. If a sector template or admin ever sets a custom `fontFamily` to an actual web font, it must be self-hosted (`app/assets/fonts/` + `@font-face`), never a Google Fonts `<link>`.

**Accessibility fixes made this phase**: `ContactForm.vue`'s inputs had placeholder-only labeling (no real `<label>`) and hardcoded English button/success/error text regardless of locale — fixed with `sr-only` `<label for>` elements tied to `useId()`-scoped input ids, and new `contactForm.*` i18n keys (`i18n/locales/*.json`) for the button/success/error strings. `Gallery.vue`/`ImageText.vue` `<img>` tags had `alt=""` (decorative) despite being real content images — now use the new `mediaAlt()` helper (`app/composables/useMedia.ts`) to read the media's actual translatable alt text, falling back through the same locale chain as `pickTranslated`. All public `<img>` tags now have `loading="lazy"` plus explicit `width`/`height` (prevents CLS); `Hero.vue`'s CSS background image gets a `<link rel="preload" as="image">` since the browser can't otherwise discover it before parsing CSS. Admin Topbar's profile-menu button and `LanguageSwitcher`'s toggle button gained explicit `aria-label`s — their previous accessible name depended on text that's `hidden` below the `sm:` breakpoint, so a screen reader (or a Playwright test, which is how this was caught) on a narrow viewport saw an unlabeled button.

**Custom error page**: `app/error.vue` (Nuxt's error-boundary convention) replaces the framework default 404/500 page with one using the real header/footer and `noindex, nofollow` — curl a 404 URL with a plain `Accept: */*` (no `text/html`) and Nitro still returns raw JSON; that's correct framework content-negotiation behavior, not a bug in this page (see it render properly with `curl -H "Accept: text/html"` or any real browser).

**E2E tests**: `playwright.config.ts` + `e2e/*.spec.ts` (`pnpm test:e2e`, requires `pnpm dev` and a seeded database already running — it does not boot its own server, since the app needs real seeded content). `e2e/global-setup.ts` upserts a fixed test admin (`e2e-admin@example.com`) directly via the DB so the suite never depends on whatever real admin accounts exist. Two projects: `chromium` (desktop) and `mobile-360` (360×740, covering the acceptance criterion that both public site and admin work at 360px). Covers: homepage + JSON-LD render, language switching to actual translated content, service detail navigation, JS-disabled SSR readability, contact form submission, admin login/logout, and a 401 check on `/api/admin/**` without a session.

**Gotcha (real bug, not a test artifact):** clicking a button immediately after `page.goto()` can land *before* Nuxt finishes client hydration — the click then falls through to the browser's native (non-JS) form submission instead of the Vue `@submit.prevent` handler, silently reloading the page instead of calling the API. Symptom: the test hangs/fails as if the click "did nothing," with no error message ever appearing, because the JS handler never ran. Fix: `await page.waitForLoadState('networkidle')` right after `goto()`, before the first interaction, in any new E2E test that fills a form. (This looked exactly like a rate-limiting problem at first — `checkRateLimit` genuinely does 429 after 10 requests/60s, confirmed by deliberately tripping it — but the actual cause here was hydration timing, not the rate limiter; don't assume rate-limiting just because repeated login attempts are involved.)

**Docker gotcha (repeat of the Phase 8 one, different trigger):** running `pnpm db:seed --template=X` twice against the *same* Docker volume without clearing tables first correctly fails with a slug-uniqueness `ForbiddenError` — seed scripts are not idempotent by design (only the admin "Apply template" flow clears tables first). This is expected, not a bug: don't re-seed a volume that already has content; use the admin template-apply flow, or drop the volume, instead.

**Lighthouse (measured, mobile, against the production Docker build, bare container with no reverse proxy):** Accessibility 100, Best Practices 100, SEO 100, **Performance 80** — short of the ≥90 target in prompt.md §13. **Real framework bug found and fixed in this pass, not just worked around:** a Nitro/Nuxt file-based route whose filename mixes a bracket param with a literal suffix in the same path segment (`server/routes/[key].txt.get.ts`, meant to match `/:key.txt` for IndexNow's key-verification file) does not get parsed the way `nitro-routes.d.ts` implies — and, far more seriously, its mere presence broke `GET /` and every other public page sitewide (confirmed twice from a clean `pnpm dev` restart; the homepage came back the instant the file was deleted). **Never name a server route `[param].<literal>.<method>.ts`** — use a middleware instead (the fix here: `server/middleware/indexnow-key.ts`, matching the existing `redirects.ts`/`markdown-export.ts` pattern of inspecting `event.path` by hand). **If you touch Docker while a host `pnpm dev` is also running:** `docker compose up` (the full production-parity stack) and `docker-compose.dev.yml` (Postgres-only, for `pnpm dev`) both default to the same Compose *project* name (the directory name) and therefore the same container name for `postgres` — bringing the full stack up **replaces** the dev Postgres container with one attached to the *different* `postgres_data` volume (not `postgres_dev_data`), even though both volumes survive untouched. Symptom: `pnpm dev`'s `/api/health` starts reporting `db: unreachable` (it's now talking to a container that's gone) — same root cause as the pre-existing "stale process on `[::1]:3000`" gotcha above, just via the DB port instead of the HTTP port. Fix: `docker compose down` the full stack, then `docker compose -f docker-compose.dev.yml up -d` to restore the dev Postgres container (`postgres_dev_data` volume, and thus your existing seeded content, comes right back).
